

PURPOSE Build a complete, reproducible Python machine-learning pipeline
that predicts photovoltaic (PV) power output in kilowatts from
timestamped sky/cloud images and timestamp-derived features. Use the
supplied project PowerPoint as the source of truth for the documented
design. Inspect the actual dataset files before making assumptions. Do
not fabricate data, metrics, filenames, image dimensions, or model
results.

IMPORTANT SOURCE-OF-TRUTH RULE The PowerPoint documents the high-level
architecture and selected model, but it does NOT specify every low-level
implementation detail. Preserve the documented facts exactly. Where an
implementation choice is necessary but not specified, make it
configurable, document it as an implementation decision, and record it
in the project README/config. Never present an implementation default as
something explicitly specified by the PowerPoint.

============================================================ 1. PROJECT
OBJECTIVE ============================================================

Build a supervised regression system to estimate PV power output (kW)
from: 1. Timestamped sky/cloud images stored inside TAR archives. 2. PV
generation measurements stored in CSV format. 3. Time-derived cyclical
features.

Documented source data: - Image archives: files matching the general
pattern 2019_*.tar - Image formats: .jpg, .jpeg, .png - Timestamp in
image filename: 14-digit string in YYYYMMDDHHMMSS format - Filename
timestamp extraction regex: () - PV CSV filename: 2019_pv_raw.csv - CSV
timestamp column: Date - Regression target column: Huang_E4102_kW -
Target unit: kilowatts (kW)

The task is regression, not classification. The model output must be a
continuous numeric PV power estimate in kW.

The presentation calls the project PV power prediction/forecasting.
However, the documented matching method aligns an image and PV
measurement from the same minute. Therefore, implement same-minute PV
estimation/prediction as the baseline. Do NOT claim future forecasting
(for example, 15-minute-ahead prediction) unless a future-shifted target
is explicitly configured and separately evaluated.

============================================================ 2. REQUIRED
END-TO-END ARCHITECTURE
============================================================

Implement this pipeline:

A. Discover and validate input files. B. Load and validate the PV CSV.
C. Stream image members from TAR archives without extracting entire
archives to disk. D. Extract the 14-digit timestamp from each image
filename. E. Parse timestamps into datetime values. F. Align image
timestamps and CSV timestamps at minute precision. G. Enforce one sample
per minute and apply a documented duplicate policy. H. Decode each image
and extract deterministic image features. I. Extract cyclical time
features. J. Concatenate image and time features into a fixed-length
NumPy float32 vector. K. Build a feature matrix X and target vector y.
L. Sort samples chronologically and split 70% train, 15% validation, 15%
test WITHOUT shuffling. M. Train
sklearn.ensemble.HistGradientBoostingRegressor with the documented
hyperparameters. N. Evaluate train, validation, and test sets using MAE,
RMSE, and R-squared. O. Save the trained model, metrics, matched sample
metadata/features, feature schema, and run configuration. P. Provide a
reproducible inference interface that applies exactly the same feature
extraction and feature ordering as training.

High-level data flow: TAR image archives + PV CSV -> timestamp
extraction and validation -> minute-level matching -> image feature
extraction + time feature extraction -> fixed-length feature vectors ->
chronological dataset split -> HistGradientBoostingRegressor -> MAE /
RMSE / R2 evaluation -> Joblib model + JSON metrics + CSV dataset
artifacts

============================================================ 5. IMAGE
FEATURE ENGINEERING
============================================================

The PowerPoint requires these feature groups: 1. RGB color statistics.
2. Grayscale brightness, contrast, and percentiles. 3. Texture features
using horizontal and vertical gradient magnitudes. 4. Color difference
channels: R-B, R-G, G-B. 5. Histograms: 8 bins each for R, G, B, and
grayscale.

The goal is to represent sky/cloud appearance numerically, capturing
brightness, color distribution, cloud density proxies, and texture
patterns.

IMPORTANT: The PowerPoint does not specify image dimensions/resizing,
exact grayscale percentile list, exact gradient operator, exact gradient
summary statistics, exact summary statistics for color-difference
channels, or histogram normalization. These must be explicit
configurable implementation choices. Do not claim they were specified by
the slides.

5.1 Image decoding and channel handling - Use a reliable image library
such as Pillow (PIL) and NumPy unless the repository already uses
another suitable library. - Convert images to RGB consistently. Handle
grayscale, palette, RGBA, and other image modes explicitly. - If alpha
is present, convert consistently to RGB; document the behavior. - Check
image dimensions and reject zero-sized/corrupt images. - Do not crop
away sky regions unless the dataset documentation defines a crop. - Do
not resize by default unless memory/performance or variable dimensions
require it. If resizing is needed, make target size and interpolation
configurable and record them in metadata/config. - All feature
extraction must be deterministic.

5.2 RGB color statistics For each R, G, B channel, compute: - Mean -
Standard deviation - Minimum - Maximum

For a channel C with N pixels: mean(C) = sum(C_i) / N std(C) =
sqrt(sum((C_i - mean(C))^2) / N) min(C) = minimum pixel value max(C) =
maximum pixel value

This yields 3 channels x 4 statistics = 12 explicitly countable
features.

Choose and document whether pixel values remain in [0,255] or are
normalized to [0,1]. Keep the same convention for training and
inference. Prefer a consistent [0,255] convention for direct image
statistics unless there is a strong reason otherwise.

5.3 Grayscale features Convert RGB to grayscale using a documented
standard luminance conversion. A common formula is: Gray = 0.299R +
0.587G + 0.114*B

Extract: - Brightness (define as grayscale mean unless project code
specifies another definition). - Contrast (define as grayscale standard
deviation unless project code specifies another definition). -
Percentiles (the PPT requires percentiles but does not name which
percentiles).

Make percentile list configurable. A reasonable implementation default
is [10, 25, 50, 75, 90], but label this as an implementation default,
not a fact from the PowerPoint. Persist the exact percentile list in
feature_schema.json and run metadata.

5.4 Texture features using gradients The PowerPoint specifies horizontal
and vertical gradient magnitudes, but not the operator or aggregation.
Implement a documented, configurable method: - Compute horizontal
intensity differences/gradient Gx. - Compute vertical intensity
differences/gradient Gy. - Compute magnitude = sqrt(Gx^2 + Gy^2), where
spatial dimensions permit. - Extract deterministic summary statistics
from |Gx| and |Gy| or gradient magnitude. Recommended baseline: mean and
standard deviation of absolute horizontal and vertical gradients, plus
mean gradient magnitude. Make this set explicit in the feature schema. -
A Sobel operator is an optional alternative if OpenCV/scikit-image is
already used; do not add a heavy dependency without need. - Ensure edge
array shapes are handled correctly (for example, np.diff reduces one
dimension). - Document gradient scaling and boundary handling.

5.5 Color difference features Create per-pixel difference maps: D_RB =
R - B D_RG = R - G D_GB = G - B

The PPT names these channel deltas but does not define summary
statistics. Convert each difference map into a fixed set of summary
statistics. Recommended baseline: mean, standard deviation, minimum,
maximum for each difference map. This yields 3 x 4 = 12
implementation-defined features. - Preserve signed differences. -
Document dtype to avoid unsigned integer wraparound. Convert channels to
a signed or floating-point type before subtraction. - Keep the exact
feature names and order stable.

5.6 Histograms Create 8-bin histograms for: - Red channel - Green
channel - Blue channel - Grayscale channel

Total explicitly specified histogram dimensions: 4 x 8 = 32 features. -
Use fixed bin edges covering the full supported pixel range. - Normalize
histograms to proportions (sum to 1) by default so image size does not
change histogram scale. This normalization is an implementation choice
and must be documented. - Use identical bin edges and normalization for
every image. - Give each feature a stable name, e.g. hist_r_00 through
hist_r_07, hist_g_00… hist_gray_07. - Test that each normalized
histogram sums approximately to 1 for valid images.

5.7 Feature naming and order - Build one canonical ordered feature-name
list. - Do not rely on dictionary iteration order from unrelated
sources. - Every sample must have the same number of features in the
same order. - Validate no NaN or infinite values occur in feature
vectors. - If feature extraction fails for an image, skip that sample
and record the reason. - Save feature schema to feature_schema.json,
including feature names, data types, formulas, percentile choices,
histogram bin edges, gradient method, image resize policy, and library
versions.

Feature count: - The PPT allows calculation of 12 RGB statistics + 32
histogram features + 6 time features = at least 50 explicitly countable
features. - The total feature count is NOT specified because the exact
number of grayscale percentiles, gradient summaries, and
color-difference summaries is not specified. - The implementation must
calculate and report its actual feature count after the schema is
finalized. Do not state that 50 is the complete feature count.

============================================================ 6.
TIME-BASED FEATURE ENGINEERING
============================================================

The PowerPoint requires six cyclical time features: - Hour sin and cos
using a 24-hour cycle. - Day-of-year sin and cos using a 365-day
cycle. - Month sin and cos using a 12-month cycle.

Use these formulas:

hour_sin = sin(2pih / 24) hour_cos = cos(2pih / 24)

day_sin = sin(2pid / 365) day_cos = cos(2pid / 365)

month_sin = sin(2pim / 12) month_cos = cos(2pim / 12)

Where: - h is hour of day (0 to 23). - d is day of year (1 to 365 for
the 2019 dataset). - m is month (1 to 12).

Use timestamp values consistently. The PowerPoint does not state whether
minute/second fractions are included in h; the baseline should use the
parsed timestamp’s hour component, unless actual source implementation
says otherwise. 2019 is not a leap year, so the 365-day cycle matches
this dataset. If generalizing to other years, decide and document
leap-year handling rather than silently changing the formula. The month
formula uses m as the 1-based month number as shown by the presentation;
preserve that convention. These six features should be named
consistently: hour_sin, hour_cos, day_sin, day_cos, month_sin,
month_cos. Test values at cycle boundaries and confirm periodic
behavior.

============================================================ 8.
CHRONOLOGICAL DATASET SPLIT
============================================================

Use the split specified by the PowerPoint: - 70% training - 15%
validation - 15% testing - Chronological order - No shuffle

Procedure: 1. Sort all valid matched samples by normalized timestamp
ascending. 2. Determine split boundaries deterministically. 3. First 70%
-> train. 4. Next 15% -> validation. 5. Final 15% -> test. 6. Do not
call train_test_split with shuffle=True. 7. If using sklearn
train_test_split, explicitly use shuffle=False only if the sequential
split semantics are preserved. A direct index split is clearer. 8. Save

are deterministic per-image calculations, so they can be extracted
independently. If any scaler/encoder/selection is added later, fit it on

split; duplicate handling must happen before splitting.

Potential time-series concern: A chronological split evaluates on later
portions of the same dataset, but it does not automatically guarantee
robustness across years or sites. Report this limitation.

============================================================ 10.
EVALUATION METRICS
============================================================

Calculate all three metrics separately for train, validation, and test:

A. Mean Absolute Error: MAE = mean(abs(y_true - y_pred)) Unit: kW.
Interpretation: average absolute prediction error.

B. Root Mean Squared Error: RMSE = sqrt(mean((y_true - y_pred)^2)) Unit:
kW. Interpretation: penalizes larger errors more strongly.

C. R-squared: R2 = 1 - sum((y_true - y_pred)^2) / sum((y_true -
mean(y_true))^2) Interpretation: fraction of target variance explained
relative to the mean baseline. R2 can be negative.

Use sklearn.metrics: - mean_absolute_error - mean_squared_error (take
square root for RMSE) - r2_score

Guard against empty splits and constant-target edge cases. Do not hide
warnings or invent values.

Save metrics.json in a clear structure, for example: { “train”:
{“mae_kw”: …, “rmse_kw”: …, “r2”: …}, “validation”: {“mae_kw”: …,
“rmse_kw”: …, “r2”: …}, “test”: {“mae_kw”: …, “rmse_kw”: …, “r2”: …} }

Also save: - Actual vs predicted values per split, with timestamps. -
Optional residual summary. - Optional actual-vs-predicted plot and
residual plot, if plotting is included. Never fabricate or prefill
performance metrics. Metrics must come from actual execution on the
supplied dataset.
